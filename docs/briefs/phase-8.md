## Design decisions (this brief resolves them)

1. **Phase 8 is tests + docs ONLY — zero production code changes (A0; justified, not defaulted).** Every defense targets surfaces that already exist: the poison regressions live in tests, the cutoffs live inside `fit`/`build_forecast`/`compute_features` (byte-pinned by Phases 3–7), immutability lives in sqlite triggers, and the guards are test-side machinery. The checkpoint must carry `git diff 1e1c1ac -- app/` **empty, exit 0** (version-local byte-pin, criterion 7). No `app/backtesting/`, no `app/evaluation/`, no `app/state/` — **new-package = none; new-predictions = none; storage = none.**
2. **Storage: NONE (A5).** No table, no column, `SCHEMA_VERSION == 1` unchanged (pinned). The Phase 9/11 forward record (forecasts-table reuse for predictions; baselines in-process re-derivable; evaluation-record table = Phase 11's schema bump; the `get_forecast()` single-row ambiguity as a **note for the Phase 9 and 11 briefs**) is written into §11 and KNOWN-LIMITATIONS now, so it is inherited, not re-argued.
3. **Docs placement: a new short `STATISTICAL-ASSUMPTIONS` §11, authored BEFORE any build code (design decision; one placement, chosen over amending §8f/§9).** Justification: (i) §§8f and §9f are phase-scoped sections already flipped to **implemented-and-tested** status — grafting forward-looking pre-registrations onto sections whose status discipline is "authored pre-build → verified implemented" would blur that record for both phases forever; (ii) the pre-declarations (A6 population/bin/ranking registrations, A7 manifest contract, A2 test-first gate, the three-step line) are **cross-stage statistical design**, which is exactly what STATISTICAL-ASSUMPTIONS exists to hold and what the constitution means by "statistical design precedes implementation" — even though Phase 8 itself ships no statistics; (iii) a fresh §11 keeps §10's Phase 7 record untouched (the single-hunk status discipline of Phases 3–7). §11 is updated to implemented reality at phase end, as usual.
4. **Poison-matrix coverage registry (A1): a pinned registry + an AST census, both with negative probes.** In `tests/test_temporal_integrity.py`: a frozen mapping of the **pinned five** history-consuming entry points — `fit`, `build_forecast`, `compute_features`, `build_decision_report`, `storage.get_forecast/verify_all` — each to an existing, real, collected poison/tamper test (the four Phase 3–7 regressions plus this phase's own immutability audit for storage). Enforcement is two-directional: (a) an AST census of every **public** function under `app/` taking a `matches` parameter (today exactly `fit`, `build_forecast`, `compute_features`) must be a subset of the registry keys — a future history-consuming entry point fails the suite until registered **and** given a poison test; (b) a pure registry-validator function rejects any entry whose poison test does not resolve. Negative probes drive both machinery functions with fake inputs (unregistered census hit; registry entry lacking a resolvable test) and assert they fail. `build_decision_report` and the storage reads are registry-only keys (no `matches` parameter — structurally history-free, which criterion pins of Phase 7/5 remain green).
5. **Cutoff-at-source behavioral probe (A1).** For `fit`, `build_forecast`, and `compute_features`: output over a **fully unfiltered pool** — including same-day siblings and future matches of the target date — is **bit-identical** (frozen `==` plus `input_digest`/`content_hash` equality) to output over the strictly-filtered pool. Same-day invisibility is **declared design, never fixed**: a source-text pin asserts the day-granularity strict-`<` discipline remains stated in the builders' docstrings (in-pattern — Phase 7 criterion 13 checks docstring phrasing), and a behavioral assertion proves a same-date match changes nothing. Intra-day ordering remains impossible by domain (KNOWN-LIMITATIONS Phase 5 item 1 rides; "fixing" this would be a domain change requiring its own brief).
6. **Scoring-guard boundary fix (A4) — the ruling's literal pattern vs. its own positive control, resolved.** The quant's pattern text `(?<![A-Za-z0-9_])tok(?![A-Za-z0-9_])` **provably fails** its own mandated positive control: `brier_score` matches neither `\bbrier\b` nor the both-lookaround form (`_` is a word char on both sides). The security intent — close the suffixed-form evasion recorded in Phase 7 item 11 — governs: the sanctioned fix is **segment-boundary** semantics, `(?<![A-Za-z0-9])(tok)(?![A-Za-z0-9])` — `_` acts as a **segment delimiter** on both sides, so `brier_score`, `x_brier`, and `_rps_` are all flagged while `log_probs`, `probability`, `dropped_mass`, `scenario_matrix` stay clean (probed app-wide: the strict-segment scan over `app/` returns **exactly** the one allowlisted line, zero new hits). The fix lands as one in-place line in `tests/test_phase7_separation.py` (the guard of record stays where criterion 13 pinned it; the new app-wide scan imports `SCORING_TOKENS` from it — single source of truth, the Phase 4/5/6 import pattern).
