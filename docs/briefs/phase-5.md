## Design decisions (this brief resolves them)

1. **Storage decision (resolves PLAN §2's deferral): sqlite via stdlib `sqlite3`.** PLAN §2 committed the proposal to "return in the first brief that needs durable state (immutable snapshots, Phase 5+)". Phase 5 needs exactly that: an immutable forecast snapshot that survives processes, that a later Phase-9/11 harness can read back bit-identically, and that cannot be silently rewritten. The condition is met; `app/storage/` and the `data/` convention are hereby **confirmed instantiated** (DOCS step updates PLAN §2). SQLite chosen over alternatives: zero-install, single-file, transactional, and — decisively — it can enforce write-once **at the schema level with triggers** (S1), which an in-memory store or a hand-rolled file store cannot. Explicitly **not** built: no ORM, no migrations framework, no connection pooling, no services/daemon, no `data/` directory created in-repo (it is git-ignored; the DB path is caller-passed — S5). Schema is one version constant (`SCHEMA_VERSION = 1`); schema evolution beyond this phase is a future brief's problem.
2. **Forecast builder signature (F1, binding): `build_forecast(matches, fixture)` — the cutoff IS `fixture.date`, computed INSIDE the builder.** There is **no `as_of`, `cutoff`, `date`, or time parameter anywhere in the signature** (the Phase 4 signature-pinning pattern: no parameter to forget; criterion 1 pins it). Internally the builder calls `fit(matches, fixture.date)` — so the cutoff is enforced twice: in the builder (which derives it from the fixture and refuses a fixture present in the matches) and in `fit` (Phase 3's internal `date < as_of` filter, unchanged). `build_forecast` raises **`ValueError` if any match in `matches` carries the fixture's natural key** (the target itself must not be history); matches dated on/after the fixture date are simply excluded by the strict filter (never an error — that is the leakage defense, exercised by the poisoned-future test). Day granularity is mandated (L1, design decision 15).
3. **Scoreless fixture representation (F5): a new frozen `Fixture` value object in `app/domain/models.py` — chosen over `score: Score | None`.** Shape: `Fixture(competition, season, date, home, away, kickoff: OptionalValue)` — no `score` field exists at all (full-precision frozen dataclass; `natural_key`/`canonical_sort_key` properties mirroring `Match`). **Justification:** (a) `Match` means *realized* result; its required `score: Score` invariant is what the fitter's goal arithmetic (`match.score.home + match.score.away`) and validation's score checks rely on — making `score` optional would weaken a Phase-2 invariant and ripple through ingestion, validation, and `fit` for no gain; (b) a forecast target that *cannot even represent* a score is structurally incapable of accidentally consuming its own result — the strongest form of F1's refusal; (c) the type distinction makes the builder's input contract checkable (`build_forecast` accepts a `Fixture`, not a `Match`). The **domain-layer edit is sanctioned here, in this brief** — the builder never improvises it: `app/domain/models.py` gains `Fixture` and `app/domain/__init__.py` exports it; **no other domain file or field changes** (Match, validation, ingestion untouched). Kickoff rides as `OptionalValue`: a missing kickoff stays `Availability.MISSING`, never defaulted (A3).
4. **`Forecast` record (F2, binding): a frozen dataclass with EXACTLY this field set, in this order:** `competition: str`, `season: str`, `date: str`, `home: str`, `away: str` (the fixture natural key, top-level), `kickoff: OptionalValue` (fixture echo; MISSING never imputed), `as_of: str` (== `fixture.date`, exactly, a date string), `fitted: FittedParams` (**full object by value**, all provenance: model_version, config, pooling, input_digest, teams, parameters, iterations, convergence_status, sample_size, insufficient flags), `lambda_home: float`, `lambda_away: float`, `max_goals: int`, `dropped_mass: float` (matrix essentials), `outcome_home: float`, `outcome_draw: float`, `outcome_away: float` (**analytic `outcome_probs`, full precision — NEVER Monte-Carlo counts or frequencies**), `forecast_version: str` (the `FORECAST_VERSION` string constant), `content_hash: str` (sha256, computed at construction). **No `seed` field exists anywhere — a `Forecast` is a deterministic object**: identical `(matches, fixture)` + model version + config ⇒ field-for-field identical `Forecast` including `content_hash` (criterion 4). The record stores enough to **re-derive the scoreline matrix bit-identically** (full `FittedParams` ⇒ `scoreline_log_probs` is a pure function of it), which is what Phase 9's bit-identity verification consumes. Matrix essentials are stored alongside both as disclosure (λs, dropped mass) and as hash-covered tamper evidence. Whether the 121 `log_probs` cells are *also* stored verbatim is open question 2 (default: no — re-derive + hash-verify).
5. **Content hash (F3, binding): a WRITTEN canonicalization spec; mismatch is a hard error, never a warning.** `content_hash = sha256(utf-8 bytes of canonical JSON)` where the canonical JSON is built from exactly the F2 fields (minus `content_hash` itself) under a fixed spec, written as code + module docstring in `app/forecasts/canonicalization.py` and summarized in STATISTICAL-ASSUMPTIONS §8: **keys sorted lexicographically** (`json.dumps(payload, sort_keys=True)`), fixed separators `(",", ":")`, `ensure_ascii=True`, no trailing newline; strings as-is; ints decimal; **floats via Python's shortest round-trip repr** (full precision, no rounding ever); bools `true/false`; enums as their `.value` strings (`convergence_status`); tuples as JSON arrays in order; `None` as `null`; nested frozen objects (`FitConfig`, `PoolingRecord`, `SampleSize`, `OptionalValue`) as nested canonical objects under fixed key names; **no timestamps, no filesystem paths, no environment values, no seed, no MC quantity may appear in the hashed payload** (AST-enforced, criterion 24). `FORECAST_VERSION` is part of the hashed content; **any change to the hashed field set, the canonicalization spec, or the derivation semantics requires a `FORECAST_VERSION` bump** — the constant is the contract's version. The **read path recomputes the hash from the stored DB fields and compares on EVERY row it returns** (not spot checks); any mismatch raises a dedicated hard error (e.g. `ForecastIntegrityError(RuntimeError)`), never a warning, never partial data (criteria 10, 11).
6. **Identity and idempotency (F4, SHOULD-FIX, adopted):** identity key = `(competition, season, date, home, away, as_of, model_version, input_digest, config, forecast_version)` where `config` is the canonical serialization of the `FitConfig` fields. Semantics on insert: **identical identity + identical `content_hash` ⇒ idempotent no-op** (row count unchanged, no error — the dedup token is the content hash); **identical identity + different `content_hash` ⇒ hard error, never an overwrite** (`ForecastConflictError`), original row untouched. A `UNIQUE` constraint over the identity columns is the schema-level backstop; a constraint violation surfaces as the same hard error. The **carried natural-key double-header limitation** (KNOWN-LIMITATIONS Phase 2 item 4) applies verbatim to forecast identity — two distinct same-day matches between the same pair are indistinguishable; recorded again in KNOWN-LIMITATIONS Phase 5.
7. **Write-once at the schema level (S1, binding):** the forecasts table is created with **`BEFORE UPDATE` and `BEFORE DELETE` triggers** whose bodies `SELECT RAISE(ABORT, 'forecasts are immutable: UPDATE refused')` (DELETE likewise) — they survive any client, **including direct `sqlite3` CLI access**, because enforcement lives in the database file itself. Criterion 8 asserts raw `UPDATE`/`DELETE` from a fresh raw connection abort. `PRAGMA foreign_keys`-style app-side measures and `set_authorizer` are **optional second layers only** (they govern app connections, not the file) — the default build ships the triggers and skips the authorizer; a future brief may add it. Additionally: an **AST scan asserts no `UPDATE` or `DELETE` SQL string touching any table appears anywhere under `app/`** (criterion 23) — the app layer does not merely avoid mutating; it provably contains no mutating SQL. **Every API read connection opens with `PRAGMA query_only = 1`** (criterion 13) — read paths are physically unable to write.
8. **No wall clock, ever, in forecast content (S2, binding):** the forecasts table has **no `created_at` or any timestamp column** (schema check, criterion 15; the hash must be recomputable from stored fields alone, and the no-wall-clock rule bars clock data in content). Timestamps exist **only** in HTTP `Date` headers (emitted automatically by the server stack — headers, never bodies) and in log lines on stderr. Any future audit trail is a **separate table outside the content-hash contract — deferred entirely this phase** (not needed yet; do not build it speculatively).
9. **Float discipline (S3, binding):** sqlite `REAL` columns store IEEE-754 doubles exactly; JSON serialization uses Python's round-trip-exact float repr. **Mandatory round-trip test:** build → store → read → recompute hash → byte-equality with the original forecast and hash (criterion 10), plus a nasty-float battery (`0.1`, `math.pi`, `math.e`, a subnormal, a 1e-300, a full-precision λ output) through both the REAL columns and the JSON tuple encodings (criterion 12).
10. **Storage operation semantics (S4, binding, one paragraph).** `insert_forecast(connection, forecast)` performs **one `INSERT` per forecast inside a single `BEGIN IMMEDIATE` transaction** that also contains the identity check, so the check-then-insert is atomic against concurrent writers (immediate mode takes the write lock up front, serializing writers instead of failing them at commit time); the idempotent no-op path performs zero INSERTs inside the same transaction shape (criterion 14 counts statements via `set_trace_callback`). Reads use short-lived plain transactions; **backup is `sqlite3.Connection.backup(target_connection)`** to a caller-passed path — the only sanctioned copy mechanism (it produces a consistent copy even under concurrent readers; copying the file with the shell while a writer is active is not sanctioned); a backup is opened and verified through the normal read path (hash recompute) in the same test. No WAL-mode mandates, no pooling: one connection per caller operation is plenty at this scale.
11. **Layering (S5, binding):** dependency direction is strictly `app/api` → `app/storage` → `app/forecasts` → `app/models` → `app/domain`, with `app/domain` at the root; `app/forecasts` stays **pure** (imports stdlib `dataclasses`/`typing`/`enum`/`hashlib`/`json` + `app.models` + `app.domain` only — no `sqlite3`, no `http`, no `os`/`sys`/`pathlib`/`io`, no filesystem access of any kind); `app/storage` imports `app.forecasts`/`app.domain` + `sqlite3`/`json`/`pathlib`; `app/api` imports `app.storage`/`app.forecasts` + `http.server`/`json`/`urllib.parse`. **Never the reverse** (AST-enforced, criterion 22). **The DB path is a caller-passed argument to the storage opener — never an environment lookup, never a hardcoded default** (the app-wide env scan already bans `os.environ`; the storage tests use `tmp_path` exclusively).
12. **API surface (A1, minimal — binding): exactly `GET /health` and `GET /forecasts/{competition}/{season}/{date}/{home}/{away}`**, serving the **stored snapshot plus full provenance** (criteria 16, 21). **Generation is NOT an HTTP verb**: no POST/PUT route exists; non-GET methods on any path return 405. The rationale, stated plainly: a compute-on-demand endpoint would create **ephemeral** forecasts that Phase 11 can never score — the whole point of durable, immutable, hash-identified snapshots is that every forecast that ever existed is scorable. If the developer later wants generation exposed, it must **store-then-serve** (insert through the write-once path, then serve the stored row) — not this phase (open question 5). Path segments are percent-decoded (`urllib.parse.unquote`); team names contain spaces. `GET /teams` is optional (open question 3, default omit).
13. **Response contract (A3/H1/A2, binding):** every forecast response is **byte-deterministic JSON** — `json.dumps(payload, sort_keys=True, separators=(",", ":"))` encoded UTF-8, full-precision floats, **no timestamps anywhere in any body** (S2) — so two GETs of the same row return byte-identical bodies (criterion 18). The payload carries, at **TOP LEVEL** (H1 — unmissable, never buried): `convergence_status`, `insufficient_data`, `insufficient_teams`, `dropped_mass` — a `SINGULAR_SYSTEM`/`NO_DATA` forecast is served **with its flags screaming at the top**, never as a silent plausible 200 — plus the full provenance echo (A3): `as_of`, `model_version`, `input_digest`, `forecast_version`, `content_hash`; and the fixture block (natural key + `kickoff` with its availability — **missing kickoff ⇒ `availability: "MISSING"`, never a default time**), the matrix essentials (`lambda_home`, `lambda_away`, `max_goals`), the analytic `outcome_probs` (named `home`/`draw`/`away` under an `outcome_probs` key — field names say **estimate/probability**, never "confidence"/"edge"/"value" — A2), and a documented **honesty companion field** `disclaimer` (H1): a fixed deterministic string stating these are in-sample estimates pending chronological evaluation (Phases 9/11), never evidence of accuracy. **Unknown fixture ⇒ 404 with an explicit JSON error body** (e.g. `{"error": "unknown_fixture", ...}`); **malformed input ⇒ 400** (bad date shape, bad percent-encoding); **NO fabricated defaults, ever** (A3). No `confidence`, `ci`, `stderr`, or uncertainty field exists anywhere (Phase 4's `mc_stderr` is deliberately not part of a stored forecast at all — MC never touches a forecast).
14. **Dependency decision (D1) — recommended default: stdlib `http.server.ThreadingHTTPServer`, zero new dependencies.** This API is read-only over already-validated frozen records: it does schema validation at the storage boundary (frozen dataclasses with `__post_init__`), so **pydantic buys nothing**, and FastAPI would drag `starlette`, `pydantic`, `anyio`, and `uvicorn` onto an offline machine for a two-route read surface. `ThreadingHTTPServer` from the standard library is adequate for a localhost research tool. **Bind address `127.0.0.1` is mandatory either way** — never `0.0.0.0`. **The no-auth posture is acceptable ONLY because of the conjunction: localhost-only bind + read-only methods + zero secrets in the system** (no keys, no user data, no betting surface); each pillar is documented, and if any one ever falls (network bind, write methods, secrets), authentication becomes a Phase-10+ brief requirement, not an afterthought. If the developer picks FastAPI (option b), the full transitive justification, `pip freeze`, `pip check`, and a PLAN §3 update are required at build start, plus an extension of AMENDMENT A2's exception map (`app.api` would import `fastapi`/`uvicorn` — the ban relocation grows accordingly), and the criteria in this brief stay framework-independent (they test routes and bytes over HTTP, not frameworks).
15. **Day-granularity cutoff (L1, mandated wording):** the cutoff is **`fixture.date`, a strict day-granularity date string, computed inside the builder** — never a fractional day, never a datetime, never a wall-clock instant. `as_of` is stored as exactly the fixture date string. **Documented limitation (KNOWN-LIMITATIONS Phase 5):** the system **cannot exploit within-day ordering even when a kickoff time is known** (two matches on the same date cannot be ordered against each other), and **cannot verify wall-clock pre-kickoff ordering at all** (the domain has no clock, only dates). The guarantee, stated precisely: **nothing dated on or after the fixture date can enter the fit** — a match dated exactly at the fixture date is excluded, matching `fit`'s strict `date < as_of`. This is honest day-level pre-match discipline, not instant-level discipline, and it is never described as more.
16. **Docs honesty — STATISTICAL-ASSUMPTIONS §8 authored BEFORE build code** (the Phase 3/4 pattern, quant-mandated): new section **"§8 Forecasts (stage 6) — forecast discipline"**, written before any `app/forecasts` code, covering: cutoff = fixture date, day-granularity, strict `<`, computed inside the builder; forecasts are **in-sample point estimates** with disclosed flags — never confidence, never validated (evidence begins at Phases 9/11); analytic-first — stored probabilities are the analytic `outcome_probs`, **MC frequencies never become stored probabilities and no seed field exists**; the scoreless-fixture representation (`Fixture` has no score); dropped-mass disclosure rides every record; `SINGULAR_SYSTEM`/`NO_DATA`/insufficient flags are reported results, not fallback estimates; the honesty-disclaimer policy; `FORECAST_VERSION` as the hash-contract version; summary of the canonicalization spec (full spec lives in `app/forecasts/canonicalization.py`). Updated to implemented reality at phase end, as usual.
